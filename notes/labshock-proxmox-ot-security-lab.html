Deploying LabShock on Proxmox: An OT/ICS Security Lab

BY DAVIDE VESENTINI (NULL0X)   //   PUBLISHED 2026-10-22   //   HANDS-ON LAB GUIDE

This guide documents a practical way to run LabShock in a dedicated Ubuntu Server virtual machine on Proxmox, using Docker Compose to launch the portal and lab components. The goal is a repeatable, contained environment for learning about operational technology (OT), industrial control systems (ICS), and defensive validation.

Important: LabShock contains services intended for security training. Keep the VM and its lab network isolated from production systems and the public internet. Do not expose vulnerable services through router port forwarding.

1. Proposed Proxmox VM

Create a new virtual machine in the Proxmox web interface. These are the settings used for this documented lab; adjust resources to your host capacity.

  • VM name: LabShock-OT
  • Operating system: Ubuntu Server 24.04 LTS (64-bit)
  • CPU: 4 vCPUs
  • Memory: 8 GiB RAM
  • Disk: 40 GiB, preferably on storage with enough free space for Docker images
  • Network: a dedicated lab bridge or VLAN, with firewall rules appropriate for your environment

For a reproducible setup, use a DHCP reservation or a static address configured consistently with your subnet. In the example configuration below, the VM address is 10.69.1.181. Replace it if your network uses a different address.

2. Install Ubuntu and prepare the VM

Install Ubuntu Server, create an administrative user, update the operating system, and verify that the VM can reach the repositories it needs.

sudo apt update
sudo apt full-upgrade -y
sudo apt install -y ca-certificates curl

Install Docker Engine and the Docker Compose plugin by following Docker's current official instructions for Ubuntu: Docker Engine on Ubuntu. Then verify that both commands are available:

docker --version
docker compose version
sudo systemctl enable --now docker

Use sudo for Docker commands unless you have deliberately configured a trusted administrative user for Docker access. Membership in the Docker group effectively grants root-level control of the VM.

3. Create the Compose project

Create a working directory and move into it:

mkdir -p ~/labshock
cd ~/labshock

Create a file named docker-compose.yml with the following configuration. The host address is explicitly bound in the portal's published port to avoid publishing it on every VM interface. Change the address to match your VM.

name: labshock
networks:
  portal_network:
    driver: bridge

services:
  portal:
    image: zakharbz/labshock-portal:latest
    ports:
      - '10.69.1.181:443:443'
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - portal-data:/app/config/
    networks:
      - portal_network

  launcher:
    image: zakharbz/labshock-launcher:latest
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
      - ./docker-compose.yml:/data/docker-compose.yml:ro
    command: ["tail", "-f", "/dev/null"]

volumes:
  portal-data:

Review the file before starting anything. The portal container receives access to the Docker socket, which can provide powerful control over containers on the VM. Keep this deployment on a dedicated host and do not treat the socket mount as a security boundary.

4. Start LabShock and verify the deployment

Pull the images and start the Compose services:

sudo docker compose pull
sudo docker compose up -d
sudo docker compose ps
sudo docker compose logs --tail=100

If the services do not start, check the Compose output and logs before changing the configuration. Useful checks include:

sudo docker ps -a
sudo docker network ls
sudo docker volume ls
sudo docker compose config

When the lab is launched from the portal, additional lab containers may be created. In the observed deployment, container names included lab-plc-1, lab-hmi-1, and lab-nginx-1, and the lab network was named lab_l2_network. Names and image versions may change between LabShock releases.

5. Open the web interfaces

From a client that is permitted to reach the lab VM, open the portal using the VM address:

  • Portal: https://10.69.1.181
  • Observed login endpoint: https://10.69.1.181:44001/login
  • Observed lab interface: https://10.69.1.181:44002/

These ports are the endpoints observed in this deployment, not a guarantee for every version or configuration. Use the actual published ports and service status from your own instance. A browser certificate warning may occur if the service uses a self-signed or locally issued certificate; verify that you are connecting to your own VM before proceeding.

6. Troubleshooting checklist

  • Portal is unreachable: confirm the VM IP, the host firewall, Proxmox firewall rules, and whether TCP 443 is listening.
  • Port binding fails: check whether another service already uses the same host IP and port.
  • Containers restart repeatedly: inspect docker compose logs, check free disk space and memory, and validate the Compose file with docker compose config.
  • Lab components do not launch: inspect the portal and launcher logs, confirm Docker is running, and review image-pull errors.
  • Browser shows a CSRF or login error: use the expected hostname/IP consistently, enable cookies, and open the portal directly rather than reusing a stale form URL. Avoid disabling security controls to bypass the error.

7. Safety and cleanup

  • Do not bridge intentionally vulnerable OT/ICS services directly onto a trusted home or corporate LAN.
  • Permit access only from the management workstation or a dedicated lab subnet; block inbound internet access.
  • Keep Proxmox management on a separate, trusted network where possible.
  • Take a VM backup or snapshot before major changes, and remember that snapshots are not a substitute for independent backups.
  • When finished, stop the services with sudo docker compose down. Review volumes before deleting them; removing a volume may erase persistent configuration.

8. Suggested next steps

Once the lab is stable, document its network boundaries and map the traffic generated by a normal lab session. Capture packet traces and relevant host logs, then compare expected activity with observed behavior. This turns the deployment into a useful foundation for OT/ICS monitoring and detection engineering.

This is a lab deployment note, not a production-hardening guide. Validate current LabShock documentation and image versions before reproducing the setup. The IP address and exposed ports above are examples from one observed environment and may not match your network.
