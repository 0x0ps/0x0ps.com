KERBEROS DETECTION & HARDENING

A concise blue-team reference for monitoring Kerberos authentication, investigating unusual request patterns, and reducing exposure from weak account configuration.

01 // Kerberos event quick reference

  • 4768 — A Kerberos authentication ticket (TGT) was requested. Review successful and failed requests and the account, client address, and result code.
  • 4769 — A Kerberos service ticket was requested. Investigate unusual service-ticket volume and service/account context.
  • 4771 — Kerberos pre-authentication failed. Repeated failures may indicate a misconfigured client, mistyped password, or an attack; correlate before concluding.
  • 4625 — Failed logon. Useful context when correlated with other identity events, though not specific to Kerberos.
  • 4720 / 4728 / 4732 — User created or added to a security group. These are not Kerberos events, but can provide important context during an identity investigation.
Query recent Kerberos pre-auth failures (PowerShell)
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4771; StartTime=(Get-Date).AddHours(-24)} | Select-Object TimeCreated, Id, MachineName, Message | Format-List

Run on a domain controller or against forwarded Security logs with suitable permissions. Local log visibility alone may be incomplete.

Query recent TGT requests
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4768; StartTime=(Get-Date).AddHours(-24)} | Select-Object TimeCreated, Id, MachineName, Message | Format-List

Tune the time window to the incident. Use structured event fields in a SIEM where possible instead of parsing rendered message text.

02 // Configuration review

List accounts with pre-auth disabled
Get-ADUser -Filter 'DoesNotRequirePreAuth -eq $true' -Properties DoesNotRequirePreAuth,Enabled | Select-Object SamAccountName,Enabled,DoesNotRequirePreAuth

Requires the Active Directory PowerShell module and appropriate directory permissions. Review exceptions with the service owner.

Review privileged group membership
Get-ADGroupMember 'Domain Admins' -Recursive | Select-Object Name,SamAccountName,ObjectClass

Adjust for the environment's actual privileged groups and tiering model. Compare output with an approved membership baseline.

03 // Signals worth correlating

  • Bursts of failed Kerberos pre-authentication from one source, especially across many accounts.
  • Authentication attempts against many nonexistent or disabled identities.
  • Unexpected AS-REP-related exposure: accounts with pre-authentication disabled, especially privileged or stale accounts.
  • Unusual service-ticket request patterns for a specific account or service, compared with its normal baseline.
  • Authentication from atypical endpoints, networks, or time windows.
  • Follow-on account creation, privileged group changes, or endpoint configuration changes close to the authentication activity.

These are investigation signals, not verdicts. Scheduled jobs, legacy applications, clock skew, password changes, and service migrations can produce noisy patterns.

04 // Hardening checklist

  • Require Kerberos pre-authentication for accounts unless an approved exception is documented.
  • Use long, unique passwords or managed service accounts where supported; reduce standing privilege for service identities.
  • Review SPNs regularly and remove stale service registrations only after validating application dependencies.
  • Use tiered administration and limit interactive logon rights for service accounts.
  • Apply account lockout and smart lockout policies thoughtfully; tune to reduce abuse without creating easy denial-of-service conditions.
  • Synchronize clocks, forward domain-controller Security logs centrally, and protect retention from tampering.
  • Alert on unusual authentication rates and privilege changes, using baselines and exclusions that are reviewed periodically.

05 // Incident triage sequence

  1. Confirm the time range, domain controllers involved, and whether the relevant audit events are being collected.
  2. Group activity by source address, target account, result code, and event volume; compare against normal patterns.
  3. Check whether affected identities are valid, disabled, privileged, service-linked, or configured without pre-authentication.
  4. Correlate with endpoint, VPN, firewall, DNS, and identity-management records.
  5. Preserve relevant events and document scope before making changes.
  6. Contain or reset credentials only under incident-response procedures, then remediate the underlying configuration and verify monitoring.
